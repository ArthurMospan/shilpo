# Шільпо — списки покупок для Сільпо

Шільпо — Telegram-асистент, який перетворює звичайний список покупок на готовий кошик Сільпо. Гість надсилає фото рукописного списку або пише товари текстом; бот читає список, уточнює незрозуміле, знаходить кожен товар у **своєму** магазині гостя з актуальними цінами, показує варіанти з фото — і складає все в кошик Сільпо за один дотик.

## Сценарій за 60 секунд

1. **Фото або текст.** Гість фотографує список на клаптику паперу. Gemini читає рукописний текст і розкладає його на позиції: назва, кількість, уточнення.
2. **Навідні питання.** Якщо почерк нерозбірливий або «кава» може бути зерновою, меленою чи розчинною — бот питає в чаті кнопками. Відповідь можна й написати словами. Про кількість не питає ніколи: її видно й міняється повзунком у Mini App.
3. **Пошук у Сільпо.** Один виклик `silpo_find_products_batch` знаходить до 30 позицій одразу — у тому магазині та зі способом доставки, які обрав гість. Тому ціни й наявність справжні, а не «десь по мережі».
4. **Вибір товарів.** Кнопка відкриває Mini App на весь екран: під кожною позицією до 20 варіантів із фото, ціною, фасовкою та знижкою. Лічильники кількості, сума оновлюється миттєво, видно доставку й мінімальне замовлення.
5. **Кошик.** Якщо в кошику вже щось є — бот питає: додати до наявного чи замінити. Далі товари летять у справжній кошик Сільпо, і гість одразу переходить до оформлення.

## Що саме робить це зручним

- **Магазин обирає гість.** За замовчуванням контекст (branch + deliveryType) береться з активного кошика Сільпо, а не вгадується. Чіп у хедері відкриває пікер: збережені адреси доставки й магазини самовивозу. Зміна магазину перешуковує весь список — показувати вчорашні картки під новою назвою було б вигадкою.
- **Адреса, якою мислить гість.** На доставці в чіпі стоїть **його** адреса, а не склад, який Сільпо призначило їй обслуговувати; філія лишається дрібним сірим рядком. На самовивозі — навпаки, адреса магазину і є суттю.
- **Дії під рукою.** Біля поля вводу — постійна клавіатура: «Новий список», «Мій кошик» і вхід у Mini App. Кнопка меню повернулася до списку команд: застосунок — це місце, де обирають товари, а не куди приземляються.
- **Мінімум питань.** Модель питає лише там, де без відповіді неможливо зрозуміти, *який* товар шукати. Проста відповідь («2», «так», «не треба») обробляється локально — без зайвого запиту до моделі.
- **Чесна ціна.** Акційна ціна для однієї одиниці замінює полицеву; мультипакет («3 шт по 25 ₴») показується окремою позначкою, бо купівля однієї штуки його не дає.
- **Кошик гостя недоторканий.** Наявні товари ніколи не перезаписуються мовчки — заміна відбувається лише після явного підтвердження. Кошик Сільпо живе в одному магазині, тож якщо гість шукає в іншому, застосунок так і каже: покласти вийде лише в порожній кошик, і очищення підтверджує саме він.
- **Видно все, що впливає на рішення:** сума, кількість товарів, вартість доставки, поріг безкоштовної доставки, мінімальне замовлення й скільки до нього не вистачає.

## Використані інструменти MCP «Сільпо»

| Інструмент | Навіщо |
| --- | --- |
| `silpo_get_my_shopping_cart` | знайти активний кошик гостя |
| `silpo_get_shopping_cart_by_id` | магазин, спосіб доставки, вартість доставки, мінімальне замовлення, вміст кошика |
| `silpo_list_branches` | публічна назва й адреса магазину, пошук у пікері |
| `silpo_get_my_delivery_addresses` | збережені адреси доставки для пікера |
| `silpo_get_available_delivery_types` | який магазин обслуговує конкретну адресу |
| `silpo_get_my_online_orders` | магазини самовивозу з історії + що гість уже брав |
| `silpo_get_my_favorites` | «улюблене» як сигнал для ранжування |
| `silpo_find_products_batch` | пошук до 30 позицій списку за один виклик |
| `silpo_add_or_update_cart_products` | додати обрані товари в кошик |
| `silpo_clear_shopping_cart` | очистити кошик у режимі «замінити» |

Авторизація — офіційна: OAuth 2.1 + PKCE з Dynamic Client Registration. Кожен гість реєструє власного OAuth-клієнта, JWT Сільпо ніколи не потрапляє в цей застосунок — назовні виходить лише короткоживучий access token, який автоматично оновлюється через refresh token.

## Технології

- **Бот і API:** Node.js 22, TypeScript, Telegraf, Express 5
- **Розпізнавання:** Google Gemini (vision + structured output) з ротацією ключів
- **Інтеграція:** Silpo MCP через JSON-RPC поверх Streamable HTTP
- **Mini App:** React 19, Vite, Telegram Web App API
- **Дані:** Turso/libSQL у production, локальний SQLite для розробки

## Локальний запуск

```bash
npm ci --prefix bot
npm ci --prefix webapp
npm run build --prefix webapp
```

Створіть `bot/.env`:

```env
BOT_TOKEN=токен_від_BotFather
WEBAPP_URL=https://публічна-https-адреса
GEMINI_API_KEY=ключ1,ключ2,ключ3
PORT=3000
```

Запуск бота разом зі зібраним Mini App:

```bash
npm run dev --prefix bot
```

Telegram відкриває Mini App лише за публічною HTTPS-адресою — для локальної розробки підійде тунель (наприклад, `cloudflared tunnel --url http://localhost:3000`), а його адресу треба покласти у `WEBAPP_URL`.

Без `TURSO_DATABASE_URL` створюється локальний `bot/database.sqlite`, який ігнорується Git.

### Перевірки перед комітом

```bash
npm test --prefix bot
npm run build --prefix bot
npm run build --prefix webapp
```

## Два режими роботи

Бот однаково працює як довгоживучий процес і як serverless-функція:

- **Webhook (production, Vercel).** Telegram сам стукає в `POST /api/telegram`, функція піднімається на час обробки й гасне. Нічого не «спить» і не потребує штучних пінгів. Автентичність апдейту підтверджує `TELEGRAM_WEBHOOK_SECRET`, який Telegram повертає в заголовку.
- **Long polling (локальна розробка).** `npm run dev --prefix bot` піднімає той самий Express-додаток плюс роздачу Mini App і тримає polling.

Serverless нічого не тримає в пам'яті між викликами, тому PKCE-стан OAuth лежить у таблиці `oauth_states`, а не в змінній процесу: `/api/auth/start` і `/api/auth/callback` можуть потрапити в різні інстанси. Обробка апдейту продовжується після відповіді Telegram через `waitUntil` — розбір фото й пошук 30 позицій довші, ніж вебхук має право тримати з'єднання.

## Деплой на Vercel

```bash
npx vercel link
npx vercel env add BOT_TOKEN production
npx vercel env add GEMINI_API_KEY production
npx vercel env add TELEGRAM_WEBHOOK_SECRET production
npx vercel env add TURSO_DATABASE_URL production
npx vercel env add TURSO_AUTH_TOKEN production
npx vercel env add WEBAPP_URL production      # публічна адреса проєкту
npx vercel deploy --prod
```

Після деплою треба один раз показати Telegram, куди слати апдейти:

```bash
npm run webhook:set https://ваш-проєкт.vercel.app
npm run webhook:info     # перевірити
npm run webhook:delete   # повернутись до локального polling
```

`WEBAPP_URL` має точно збігатися з публічною адресою: за нею Telegram відкриває Mini App і на неї ж Сільпо повертає OAuth-код. Перевірити можна на `/api/health` — він віддає і адресу, і тип бази, і режим роботи.

**Альтернативи:** `render.yaml` і `Dockerfile` лишились у репозиторії для запуску довгоживучим процесом. Там бот працює на long-polling, і на безкоштовному плані Render сервіс засинає без трафіку — знадобиться зовнішній пінг.

## Структура репозиторію

```text
bot/
  src/ai/          Gemini: ротація ключів, розбір списку, уточнення
  src/silpo/       MCP-клієнт, OAuth, магазин, пошук товарів, кошик
  src/lists/       стан списку, питання, відповіді, підсумковий вибір
  src/bot/         Telegram-флоу та форматування повідомлень
  src/server/      Express-додаток (API, OAuth, вебхук) і локальний запуск
  src/db/          Turso/SQLite
webapp/            React Mini App: домівка, пікер товарів, вибір магазину
api/               точка входу Vercel: одна функція на весь /api/*
scripts/           реєстрація Telegram-вебхука
vercel.json        production-деплой
render.yaml        альтернатива: довгоживучий процес
Dockerfile
```
